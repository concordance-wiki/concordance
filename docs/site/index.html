What your files already know about each other.

Your team writes markdown for the AI. Concordance turns it into a wiki for the humans. Point it at your git repositories and get a site where every word of your business has a page: the note someone wrote, if any, and every passage, in every file, that mentions it.

The rail is calculated, not written: the neighbourhood map, the quoted passages and their line counts all come from reading the corpus. Written links and recognised words stay visually distinct, so you always know which of the two you are looking at.

One command

No rewriting, no wikilinks, no frontmatter required, no server to run. The build reads your repositories exactly as they are and writes a static folder you can publish anywhere. 

# turnkey, with the container image
docker run --rm -v "$PWD:/wiki" concordancewiki/concordance build

# or in a pipeline, with the command line
npx concordance build      # clones the sources, builds dist/
npx concordance lint       # checks one repository before you push

How it works

  1. Declare your repositories. One concordance.yaml lists the git sources. Nothing else is required.
  2. Build. Every word people actually use gets a page, every file that mentions it gets a link, office documents and transcripts get a preview.
  3. Publish the folder. dist/ is static: GitHub Pages, GitLab Pages, a bucket, or a file on disk. Search works without a server.

Repositories

The engine lives in one repository. The project's own wiki is built with Concordance from two content repositories and one configuration repository: copy the configuration to start yours.

  • concordance engine The command line, the packages, the plugins, the specification and the guides. ↗
  • demo-wiki configuration The configuration, theme and pipeline that publish the demo site. ↗
  • demo-glossary content Terms and rules of a fictional organisation, one note per word. ↗
  • demo-specs content Functional and technical specifications — screens, processes, rules — citing the glossary. ↗
  • demo-* planned Meeting transcripts, office documents, decision records. Each kind of content is handled on its own terms, and each adds links the others did not have.

It fits repositories you already have

Nothing to migrate, nothing to rename. Three levels, and you stop wherever it is enough.

Recognised on its own
Markdown, office documents, transcripts and interface contracts are picked up by extension. A first build works on an untouched corpus.
Declared once, in the configuration
A type per folder, or a glob when folders are not enough — specs/screens/** becomes screens. Sources, domains, thresholds and formatting live in concordance.yaml, never in your files.
Refined in frontmatter, when you want more
A few keys per note override the rules and declare relations by hand. It is the advanced level, not the entry ticket — a corpus without any frontmatter still builds.
Published under your own name
Concordance is white label: name, logo, accent colour, radius and typefaces come from a theme file, and a stylesheet of your own goes further. The site wears your identity — the visible branding is yours, the licence notices stay where the licence requires them (GPL v3).

What it does not do

Worth knowing before you install, rather than after.

  • —It is not an editor. Concordance never writes to your files: you fix things in the forge, as usual.
  • —It is not a modelling tool. No derived diagrams, no matrices, no global graph in this version.
  • —Search matches prefixes and does not correct typos. That is the price of going fully static, and it is a deliberate one.
  • —The first build is slow, because it converts every office document. Later builds take seconds.
